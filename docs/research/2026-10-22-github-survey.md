# SOE Radar：GitHub 调研与首版建议

调研日期：2026-10-22（北京时间）
已确认范围：全国国央企校园招聘优先，项目每年持续复用。首批可聚焦当季招聘，年份与届别不能写死；多届别、春招、秋招、补录及历史记录同时保留。跨年度具体约束见 [跨年度使用要求](../requirements/multi-year.md)。
工作性质：开源项目检索、README 与关键代码审阅、公开元数据及部分 Actions 状态核验；没有部署或运行这些项目的完整采集流程。

## 1. 结论

有可参考的开源项目，但本次检索和代码抽查未发现可以直接证明“覆盖全国全部国央企、截止时间准确、持续更新”的现成方案。这是本次调研的结论，不代表 GitHub 上不存在其他项目。

建议产品定位为：**帮助应届生找到仍值得投递的国央企校招机会，并能核验截止时间、发现延期和避免漏投。**

优先建设企业名录、信源维护、日期证据和变更处理。页面筛选和日历属于这套数据能力的出口。

## 2. 检索方法与边界

- GitHub 仓库搜索：国企 招聘、央企 招聘、国央企、校招 截止、state owned recruitment China。
- Web 补充检索：GitHub 上的国央企招聘、校招汇总、岗位爬虫。
- 筛选并阅读了 10 个相关候选，重点比较下列 6 个；其余作为补充。
- 对 guoqi-radar、job-radar、recruitment-radar 的日期、模型或采集代码进行核对；对 guoyang-pro 核对日历数据与国聘适配器；对 xiaozhao-radar 核对同步脚本及文件目录。
- 仓库 Star、README 里的覆盖数、一次 workflow 成功，均不能证明数据准确或信源全部有效。
- 检索不是穷尽性调查；没有对第三方站点发起全量采集。
- 具体审阅文件与 SHA、公开元数据摘录见同目录 sources.json。

## 4. 与截止时间直接相关的代码发现

### 4.1 日期区间可能被提成开始日

在 [job-radar 的 gov_notice.py](https://github.com/Jasmine-Liu-min/job-radar/blob/main/job_radar/adapters/gov_notice.py) 中，日期上下文正则匹配到第一个完整日期结束。后续虽然尝试取匹配片段内的最后日期，但日期区间的终点并未包含在该片段中。

使用与该实现相同的正则做独立合成样例复现：

| 合成输入 | 规则输出 | 应有处理 |
| --- | --- | --- |
| 报名时间：2026年9月1日至2026年10月31日。 | 2026-09-01 | 报名开始 9 月 1 日，报名截止 10 月 31 日 |
| 网申截止另行通知。毕业时间须不晚于2027年7月31日。 | 2027-07-31 | 投递截止未公布；毕业时间单独保存 |

第二例来自该实现的兜底策略：出现截止语义但未匹配到上下文日期时，从正文日期中选最大值。这只能证明规则存在误提场景，不能推断仓库全部现有数据都错。

### 4.2 不明确的截止被折叠为在招

[guoqi-radar 的 lib/agent.ts](https://github.com/sespoir/guoqi-radar/blob/main/lib/agent.ts) 按截止日期和公告年龄判断 active/expired；没有截止日期、发布时间也缺失时，可落入 active。对截止提醒产品，这种状态不足以表达“还没有证据确认是否仍可投”。

同文件使用 source_url 定位记录，能够更新单篇公告，但独立发布的延期公告是否对应原批次，需要额外的业务关联。

### 4.3 同名岗位跨届、跨批不能直接合并

[job-radar 的 normalize.py](https://github.com/Jasmine-Liu-min/job-radar/blob/main/job_radar/normalize.py) 以公司、职位、城市形成主去重键。同公司同城市每年重复发布相同岗位时，需要届别、招聘批次或官方职位标识参与区分。

### 4.4 爬虫维护是实际持续成本

[job-radar 的健康报告](https://github.com/Jasmine-Liu-min/job-radar/blob/main/data/health_report.json) 在 2026-10-22 的快照中列出国家电网、工商银行、中国石化等来源 blocked/not_run，也检测到若干来源抓取量骤降。来源配置存在，不代表当日已成功巡查。

## 5. 官方公告揭示的数据难点

- [国家能源集团 2027 届统招公告](https://zhaopin.chnenergy.com.cn/annc/showgg?id=6a152f40-7fe5-460e-ad37-0024acafd8c9)：同文存在年龄计算截止日期 2027-07-31，以及网上报名区间 9 月 2 日至 10 月 7 日。年份要结合公告发布日期及批次判断，不能把年龄截止当成网申截止。
- [中国银行 2027 年全球校招公告](https://www.boc.cn/aboutboc/bi4/202609/t20260903_25689311.html)：该公告载明北京时间 2026-10-09 24 点截止。2027 届对应的投递年份是 2026；24 点应规范为次日 00:00，同时保留原文。这里只讨论该公告表述，不据此断言没有后续变更。
- [中铝部分岗位延期公告](https://zlwebsite.chinalco.com.cn/pub/zljt/xwzx/xwzx_gsgg/202608/t20260806_175052.html)：示范了延期可单独发布、只适用于部分岗位。它是内部招聘，不能混入首版校招机会池，但可用于检验变更建模。
- 国资委名录只用于相应监管范围的企业识别，不能当作全国全部国有企业名录。还需纳入财政部相关名录、地方国资委与企业官方组织关系。
- [财政部履行出资人职责的中央企业名录](https://zcgls.mof.gov.cn/zhuantilanmu/czblz/202108/t20210817_3745862.htm) 提供其他类别及中央金融企业名录入口。
- [国资委监管企业产权信息查询说明](https://wap.sasac.gov.cn/n2588030/n2588944/c26506339/content.html) 可辅助核验央企所属关系；查不到不能直接判定为非国企。

## 6. 推荐产品范围

长期目标可以是尽量覆盖全国国央企校招。首版必须公布已覆盖名录和巡查状态，不能把“全部”作为尚无证据的宣传语。

建议按以下顺序扩展，保持全国方向：

1. 30–50 个高关注招聘主体/集团的官方入口，覆盖电力、能源、通信、建筑、交通、金融、科研制造等行业。
2. 补齐对应集团的省公司、子公司、研究院所和具体批次。集团覆盖与下属招聘主体覆盖分别统计。
3. 扩展全国省级国资系统的重点企业；逐步增加市属国企和长尾单位。
4. 对所有进入名录的单位记录“已监测、待接入、采集异常、最近成功时间”，把盲区展示出来。

不按计算机专业限制入库，专业只作为用户筛选条件。默认校招，社招、内部招聘、实习和拟录用公示分别分类，避免污染结果。

## 7. 核心模型与处理规则

建议将下列对象分开：

- 企业：正式名称、别名、上级集团、企业性质、性质核验来源、核验日期。
- 招聘项目/批次：届别、春招/秋招/提前批/补录、招聘主体、公告发布时间。
- 岗位：官方职位 ID、工作地点、专业、学历、适用批次，岗位有独立截止时覆盖批次默认值。
- 原始文档：官方/转载来源、公告 URL、投递 URL、抓取时间、原文快照与哈希。
- 截止声明：类型、原文、日期/时刻、时区、精度、适用对象、证据位置、审核状态。
- 变更事件：延期、提前关闭、重新开放、取消；关联原批次及受影响岗位。
- 用户提醒：关注条件、已投状态、已发送事件，防止重复提醒。

截止类型至少区分：明确日期、明确时刻、滚动招聘/招满即止、长期招聘、未公布、来源冲突待核验。

招满即止与长期招聘不能仅因文本不含日期就互相替代。招聘开放状态、截止声明类型、数据核验状态也不要混成一个字段。

默认使用 Asia/Shanghai。只写日期时保留 date 精度，不伪造官方 23:59:59；倒计时以“当日截止、具体时刻未公布”呈现。只写月日时结合公告发布日和批次推定年份，记录推定依据，不确定则进入审核。

只有对应同一主体、批次和适用岗位的后续官方通知，才更新有效截止。官方证据相互冲突且无法解释时保留双方并暂停精确倒计时。转载先进入线索池，核验后再给出“官方已核验”标签。

去重优先使用官方职位/公告标识；跨来源通过招聘主体、届别、批次、岗位及适用地域建立关联，保留各来源声明。不同地区或独立截止的岗位不可被简单合并。

## 8. 数据链路与技术建议

企业名录 → 信源配置 → 采集原文 → 分类与日期候选提取 → 规则校验/必要人工审核 → 关联与变更识别 → 页面/日历/提醒。

建议从 Python 采集与解析、SQLite、本地定时任务、简单 Web 查询开始。公开 JSON/HTML 优先，动态站点按需使用 Playwright，PDF/图片按需 OCR。

- 将适配器按招聘系统/站点结构复用，而非给每个企业复制一套代码。
- 保留原文快照、抽取版本和证据，站点变更时可重跑解析。
- 规则处理清晰格式；LLM 辅助处理复杂正文时必须返回原文片段与位置。模型自报置信度不能替代校验。
- 无变更内容不重复调用模型，控制采集和抽取成本。
- 搜索引擎、公众号、公开共享表格用于补充发现，最终回溯官方公告；难以自动获取的内容提供人工提交入口。
- 采集失败、分页不完整或列表短暂清空时，保留已有记录并标记数据过期，不自动把所有岗位判为关闭。
- 每个源记录成功/失败、最近成功时间、条数变化、分页完成情况。HTTP 200 和任务成功不是数据质量标准。
- 后续多人使用、订阅并发和数据量增长后再迁移 PostgreSQL、增加任务队列。

上述为方案建议，不是已完成的实现，也没有验证某个第三方 API 当前一定可用。

## 9. 首版用户功能

1. 截止列表：今天、3 天内、7 天内；明确显示已核验和待核验。
2. 筛选：届别、地区、行业、集团/子公司、学历、专业、批次。
3. 详情：截止原文、官方公告、投递入口、最后核验时间、变更记录。
4. 关注：收藏、已投/未投、按条件保存；提醒在用户配置渠道后启用。
5. 日历：仅对明确且已核验的截止导出 ICS；未公布/滚动招聘不生成虚构事件。
6. 维护后台：缺日期、冲突日期、抓取异常、待确认企业性质与人工纠错。

第一屏重点回答：哪些快截止、哪些刚新增或延期、我还没投哪些、哪些信息需要重新确认。

## 10. 建议实施顺序与验收

阶段 A：信源与数据验证
- 建 30–50 个招聘主体的名录及官方入口，明确集团与子公司粒度。
- 从多个行业人工整理 100–200 份公开历史/当前公告做验证集，包含 PDF、图片、无年份、日期区间、延期、多岗位截止等。
- 给每份样本标注真正的网申截止、适用范围和证据；区分训练/调规则样本与留出的验证样本。

阶段 B：最小采集闭环
- 实现少量官方来源适配器、原文保存、日期抽取、审核和异常报告。
- 先验证“抓到、提对、可追溯、能更新”，再扩大覆盖面。

阶段 C：可使用首版
- 完成查询列表、筛选、证据详情、收藏与日历导出。
- 增加临期提醒、延期提醒及发送去重；真实发送需使用者配置渠道。

阶段 D：扩源与运营
- 按官方名录和招聘活跃度补齐集团子公司、省属企业，增加投稿纠错。
- 连续观察来源成功率、延迟、日期错误与用户漏投反馈。

建议验收门槛（待实际样本验证，不是现有成绩）：
- 对外标为“官方已核验”的明确截止，100% 有可定位证据。
- 留出集上已发布明确截止的精确率目标至少 98%；同时报告明确截止召回率与弃答率，不能靠全部留空换高准确率。
- 覆盖率按“公开声明范围内已接入的招聘主体 / 该范围名录主体”计算，集团与子公司分开，不能宣称全国真实机会召回率。
- 监测异常、未公布日期和来源冲突能被看见。
- 代表性源连续运行至少 7 天，观察新增、更新、失败恢复和延期流程。
- 同一延期/临期事件不重复发送；已投用户可关闭相关提醒。

开发周期先用数据试采确定：动态站比例、PDF/图片比例、来源维护量和人工审核量会直接影响进度。本次没有足够依据给出固定工期或运行预算。

## 11. 复用建议

自建以截止声明和招聘批次为核心的模型，优先借鉴：

- guoqi-radar：官方性分级与官方回溯。
- job-radar：适配器、审核入口、信源健康和增量处理的设计。
- recruitment-radar：来源维护和人工确认后台。
- guoyang-pro：静态企业名录与动态招聘数据分离。
- JobHunter / campus-radar：模块化采集、导出、增量日报。

直接引入代码前核对文件许可。此次确认 guoqi-radar、JobHunter 有 MIT LICENSE，xiaozhao-radar 有 Apache-2.0 LICENSE；job-radar、recruitment-radar、campus-radar、job-scraper、guoqi-jobs 所查树未见明确许可证文件。guoyang-pro README 声称 MIT，但所查根元数据未给出明确 license，本次不把它当已确认代码授权。代码许可与第三方招聘数据可复用范围分别核对。
