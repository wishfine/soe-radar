# 跨年度使用要求

确认日期：2026-10-22（Asia/Shanghai）。

用户要求：全国国央企校招优先；整个项目每年都可以用。本文是后续实现的产品和数据约束，尚不代表功能已经实现。

## 1. 目标与范围

同一部署、同一数据库、同一套采集框架可以连续跨年运行。不需要每年复制仓库、清空数据库或修改代码中的固定毕业年份。

首批采集可关注当季招聘，系统本身不能只支持某一届。历年数据保留用于查证、纠错和研究招聘节奏。

每年复用需要持续维护来源和解析器：企业入口改版、年度专题迁移或招聘规则变化仍可能需要更新配置或代码，不能把“每年可用”解释为永久免维护。

## 2. 分开表达时间概念

| 概念 | 含义 | 设计约束 |
| --- | --- | --- |
| 公告发布时间 | 文档对外发布的日期 | 保留来源及精度，与抓取时间分开 |
| 毕业届别 | 可报名的毕业群体 | 多值或有明确依据的范围；未知可为空，不强行推定 |
| 招聘项目 | 某单位一次招聘活动 | 使用稳定内部 ID，可关联多篇公告、多届别、多批次 |
| 招聘季/项目年度 | 官方所称秋招、春招及年度 | 保留官方表述；与自然年、毕业届别分开 |
| 批次 | 提前批、正式批、补录等具体轮次 | 保留原始名称，并提供规范标签；同类标签可有多轮 |
| 报名开放与截止 | 具体投递窗口 | 按批次或岗位表达，支持延期、重开和提前关闭 |
| 采集/核验时间 | 系统何时观察或确认数据 | 用于新鲜度判断，不能作为缺失公告年份的唯一依据 |

示例：2026 年发布的 2027 届秋招和 2027 年发布的 2027 届春招，属于相同届别的不同招聘活动或批次。同一企业面向 2027、2028 届的活动也可能重叠开放。

不能仅以“当前自然年 + 1”认定毕业届别，也不能假设所有企业在同一个月份开启新招聘年度。

## 3. 数据标识与历史保留

- 企业实体独立于年份；正式名称、别名及上级集团关系应能记录生效时间，适应更名与重组。
- 招聘项目、批次和岗位具有独立内部 ID，不以公司名、岗位名、城市三项直接跨年合并。
- 官方职位 ID、公告 ID 和 URL 是来源标识，可能被复用；匹配时同时核对活动、批次和届别上下文。
- 相同 URL 次年改成新一届内容时，保留原文版本；确认是新活动后创建新项目，不把去年的截止更新成今年。
- 同一次招聘接受多个届别时，建立届别关联，不复制出若干重复机会。来源未知时保留未知。
- 同批次延期属于变更事件；次年同名招聘属于新活动。批次不同的补录可关联原项目，但单独保存窗口。
- 过期记录可归档，归档不得删除公告证据或往届数据。新年度开始不执行年度清库。
- 数据结构使用迁移管理，升级前备份，保持历史记录可查询。

## 4. 日期解析与证据

- 保存原始截止文本、标准化值、时区、日期精度、证据位置、适用对象及抽取版本。
- 日期计算使用可注入的当前时间，展示默认时区为 Asia/Shanghai。
- 缺少年份时优先依据公告发布上下文、官方项目和完整时间区间判断；跨年区间需要同时解析起止端点。
- 无法确定年份时进入待核验，不使用运行机器当前年份直接补齐。
- “2027 年 7 月前毕业”等资格日期与报名日期分开。
- “招满即止”、长期招聘和未公布保持不同类型，不为它们制造年度截止日。
- 第三方表格中的“尽快投递”等催投建议与截止声明分开保存；不能直接将它们判定为“招满即止”。接入时保留上游原始文本并回查官方证据。
- 对旧公告重跑新版解析时，记录新的抽取结果与证据，保留原有审核及变更记录。
- 历年日期只能提供标注清楚的参考窗口，不能自动变成今年已确认的截止时间。

## 5. 来源配置与跨年发现

企业名录、来源配置和采集器分开管理。企业保持稳定，年度入口可以变化。

- 来源区分长期入口和年度专题入口，记录有效期、所属活动和最近核验时间。
- 优先从长期官网入口发现新的招聘项目；确有规律的年度 URL 模板也必须检查页面届别和实际内容。
- 不因把 URL 中的年份替换后返回 HTTP 200 就认为新一届招聘已经开启。
- 搜索关键词按可配置的届别集合生成，覆盖同时活跃的多届招聘，不全局替换年份。
- 新年度未找到公告时显示尚未发现，不能直接断言企业未开展招聘。
- 抓取失败、分页未完成、年度入口迁移与真实关闭分别表达。监测失败不批量关闭已有岗位。
- 重点巡查仍开放或临近截止的活动；历史活动降低频率，保留补充更正的入口。

## 6. 页面、筛选与订阅

- 首页默认展示当前日期下仍开放、即将开放或需要确认的机会；未知状态单独标识。
- 届别支持多选及未知项，不将元旦作为所有用户的届别切换点。
- “某届秋招”“往届可投”等快捷视图由届别、招聘季与开放状态配置生成，视图标题不作为主键，也不在代码中逐年复制。
- 可按招聘季、批次、发布时间及是否归档筛选；提供历年查询。
- 今年仍有效的跨年活动继续展示；上一届明确过期活动不混入默认可投列表。
- 当届和往届数据均展示官方原文与最后核验时间，避免将历史页面包装成今年公告。
- 用户可选择关注特定届别，或主动订阅后续年度。固定届别订阅不自动改成下一届。
- 收藏和已投状态绑定具体招聘机会。去年投过的同名岗位，不能让今年的新活动自动变成已投。
- 提醒去重绑定具体机会、批次和提醒事件。重开或延期后重新计算提醒，但每个有效事件只发送一次。
- 跨年迁移页面、缓存、导出文件或定时任务时，不丢失订阅、历史状态或上次成功采集状态。

## 7. 覆盖统计

分别统计企业名录覆盖、当前活动覆盖、来源新鲜度与明确截止证据完整率，避免用多年累计公告数量冒充当年覆盖。

集团和下属招聘主体分开统计；不同届别、招聘季使用可解释的统计口径。保留年度快照，企业重组不回写改变往年的统计依据。

## 8. 实现验收场景

这些是后续实现必须验证的行为，不是当前已通过的测试。

1. 同时保存同公司 2027 届和 2028 届同名同城岗位，互不覆盖。
2. 同时保存同届秋招、春招、提前批和补录，分别呈现窗口及变更。
3. 一次招聘接受多个届别，筛选任一符合届别都能找到，提醒不重复。
4. 从 12 月 31 日切换到 1 月 1 日，跨年开放的岗位继续可见，历史与用户状态保留。
5. 对 12 月发布、报名至次年 1 月的公告正确处理跨年区间；证据不足时弃答。
6. 次年重读旧公告，不将旧的月日截止直接改为今年。
7. 官网沿用同一 URL 发布新一届招聘，旧证据与旧活动仍可查询。
8. 年度专题失效或采集异常时，报告来源问题，不将所有机会视为已关闭。
9. 去年已投过的岗位，今年新活动保持未投状态；固定届别订阅不自动变更。
10. 延期、重开和新年度新批次分别关联、提醒，并正确去重。
11. 归档后能查到历年日期、原文证据及全部变更。
12. 配置新的目标届别后，采集、筛选、导出和调度使用同一套实现，无需复制工程。
